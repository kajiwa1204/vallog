# Vallog — スコアリング設計

## カテゴリ構成

| カテゴリ | 種別 | デフォルト重み |
|---|---|---|
| GitHub活動量 | スコア対象 | 40% |
| タスク完了スピード | スコア対象 | 35% |
| 品質・可用性 | スコア対象 | 25% |

> 重みはチームごとにカスタマイズ可能

---

## 各カテゴリの指標

### GitHub活動量（40%）

| 指標 | 詳細 |
|---|---|
| Issue / PR 立ち上げ数 | 設計・デザイン・リファクタへの関与も含む |
| コードレビュー貢献 | コメント1件以上のレビューのみカウント |
| Approve / Request changes 回数 | 自分のPRへのセルフレビューは除外する |
| ターンアラウンドタイム | PR到着からレビューまでの時間。自分のPRへのセルフレビューは除外する |

カテゴリ内の合成: **均等割り**（後から調整可）

> 均等割りの4指標のうち3つ（レビュー貢献・Approve/Changes・TAT）はレビュー系のため、カテゴリ内は実質「起票 25% : レビュー 75%」の配分になる。MVPはこのまま運用し、実データを見て調整を判断する。

---

### タスク完了スピード（35%）

| 項目 | 詳細 |
|---|---|
| 計測式 | メンバー単位の 総獲得SP ÷ 総経過時間（タスク分割数に中立にするため、Issueごとの速度を足し上げない） |
| SP入力方法 | GitHub IssuesのラベルでSPを設定（例: `SP:1` / `SP:2` / `SP:3` / `SP:5` / `SP:8`）|
| 計測区間 | アサインからIssueクローズまで（PRマージによる自動クローズを想定）。Issue↔PRの紐付けはキャッシュに持たないため、クローズ時刻をマージ時刻の代理とする |
| 帰属 | Issueのアサイン先に帰属する。アサインのないIssueはSPが誰にも計上されない。PR↔Issue紐付けやクローズ実行者には依存しない |
| 前提 | **GitHub Projects運用**を必須とする |

- **Issueに紐付かないPR**はスピード評価の対象外（SPラベルはIssueにしか付かないため測定不能）。該当作業は活動量・品質カテゴリで評価される。
- **`state_reason`**: `not_planned`（着手せず却下・重複等）でクローズされたIssueはSPを計上しない。`completed`（手動クローズ・PRマージによる自動クローズ）のみ対象。
- **アサイン時刻の代替**: `/issues/events` の取得上限で `assigned_at` が得られない場合はIssue作成時刻を起点にフォールバックする（獲得SPを捨てないため）。
- **経過時間の下限**: アサイン直後クローズによる巨大値を防ぐため 0.1h でクランプする。

---

### 品質・可用性（25%）

| 指標 | 詳細 |
|---|---|
| 機能ごとの可用性スコア | 実装者以外のメンバーがレビュー・検証（他者にApproveされたマージ済みPR数を代理指標とする。セルフApproveは除外） |
| 手戻り率 | **PR再オープン回数のみ**で計測（PR作者に帰属）。設計上は「バグ報告数 + PR再オープン回数」だが、バグ報告を正しい原因者に帰属させる手段がキャッシュに無いため、MVPは再オープンのみとする。バグ報告数の帰属方式は #75 で設計する |

---

## スコア正規化

各指標の相対スコア = メンバー個人の値 ÷ チーム全体の合計値

> 例）チームのPR合計20件のうちAさんが5件 → Aさんの相対スコア = 5/20 = 0.25

この方式により、チーム規模や活動量に依存せず、メンバー間の相対的な貢献度を公平に比較できる。

---

## 分配シミュレーション

- 各メンバーの分配比率 = 総合スコア ÷ チーム全体の総合スコア合計（AIは使用しない）
- チームはスコアと貢献サマリー（Feature D）を並べて読み、議論して分配を決める
- **スコアは配分の出発点であって、分配額そのものではない。** 最終的な分配の決定はチームが行う

## Goodhart対策とスコアの事後開示

> 「測定が目標になると、それは良い測定ではなくなる」（Goodhartの法則）。定量指標は活動量であって成果ではない。

Vallogは評価に報酬を紐づけるため、Goodhartの圧が最大化する（スコアが上がると分配が増えると学習された瞬間、SPラベルの水増し・PRの細切れ化・ラバースタンプApproveが起こる）。

**方針: 指標を賢くして対抗するのではなく、報酬のクリティカルパスから指標を外し、人間の判断を挟む。** Goodhartが噛むのは指標が「①ターゲット ②固定 ③事前既知」のとき。1本折れば圧は下がる。

| 折る足 | 施策 | 状態 |
|---|---|---|
| ①ターゲット | 分配の最終決定は人間。スコアは配分の出発点に留め、確定までに人の調整を挟む | 実装済み（分配シミュレーション。ただし下記の非対称あり） |
| ③事前既知 | スコアは作業期間中どこにも出さない。ダッシュボード（画面4）・メンバー詳細（画面5）はスコアを持たず、振り返り/分配（画面7）で初めて開示する | Phase 1で実装（#13・#14・#100） |
| ②固定 | 重みはチームがカスタマイズ可能（当初からの要件）。分配案ごとに重みを事後調整し複数案を比較する | 設計済み（`projects` にデフォルト重み・`distribution_proposals` が案ごとに重みを保持／画面3・7） |

重みは③の例外で、作業期間中も画面3で参照・変更できる。②固定を折るにはチームが重みを動かせる必要があり、また重みはチーム共通の配分ポリシーであって個人のスコアではないため、これを見ても自分の順位は分からない。

> **①ターゲットの非対称性（既知の弱点）**: 「分配の最終決定は人間」は、**人が能動的に動かして初めて成立する**。分配案の初期比率はスコアそのままなので（`services/distribution.py` の `_score_based_ratios`）、放っておけば「スコア＝分配額」がそのまま通る。既定値は合意されやすいため、①は仕組み上折れているのではなく、チームが実際に議論した場合にだけ折れる。
>
> 初期値を均等割りにすればこの非対称は消えるが、スコアに沿って分配したいチームにとっては毎回入力し直す手間になり、大多数のケースで使い勝手を損なう。そこで**禁止ではなく可視化**で対処する。既存の「編集履歴を全員に公開する」と同じ考え方で一貫させる。
>
> - 未確定のうちは「この配分はスコアをそのまま入れた出発点です」と表に明示する
> - 一度も調整されずに確定した案は「調整なしで確定」として記録に残す（編集履歴が0件のまま確定した状態）
>
> これは①を折るものではなく、**折れていないことを見えるようにする**施策である。効果が足りなければ初期値の設計に戻ること。

**UX原則: 数字を主役にしない。** ダッシュボード（画面4）・メンバー詳細（画面5）の主役は「数字に潰す前の変化ログ」（後述）とし、**スコアは載せない**。スコアが現れるのは分配画面（画面7）だけ。

> **画面7内での配置について**: 当初は画面7の中でもスコアを「下部に小さく」置くと決めていたが、#100 の開示ゲートを実装した時点でこの制約は外した。**位置で守っていた③事前既知の担保が、APIの側に移ったため**である。作業期間中は `/scores` が 403 を返すので、画面のどこに置いても見えない。開示が許された文脈（未確定の分配案がある＝分配を議論している最中）まで来たら、そこから先の配置は位置で守る必要がなくなった分だけ読みやすさに寄せてよい。
>
> 画面7ではスコアと貢献サマリーを同列に横並びで置く。どちらも同じ活動を別の粒度で言い直したもので、片方を先に読ませる理由がない。数値の隣に文章があると「なぜこの数字なのか」をその場で照らし合わせられる。
>
> **ただし ①ターゲット への対策は位置と無関係に効かせ続ける必要がある。** スコアがそのまま分配額になることを防ぐのは配置ではなく、「分配の最終決定は人間」＝全員が自由に調整でき、調整には理由の入力が必須、という仕組みの側。ここを緩めると①が立ち上がる。

折りたたみでの併置（同じ画面にスコアを置き、既定で閉じておく）は採らない。開けば見える以上 ③事前既知 は折れておらず、「隠している」という体裁だけが残るため。代わりにダッシュボードは「チームがいま何を動かしているか」を映す面に振り、個人の順位を読み取れる要素を置かない。

### 「振り返りのとき」の判定（実装済み・#100）

③を折る施策が画面配置の慣習にしか支えられていない状態を解消するため、**「振り返りのとき」を未確定の分配案（`finalized = false` の `DistributionProposal`）が存在することで判定する**。

```
案が0件                    → スコア非開示（作業期間中）
未確定で最近動いた案がある → スコア開示（分配を議論している最中）
全部確定済み               → スコア非開示（議論が終わった）
未確定だが30日動いていない → スコア非開示（議論が立ち消えた）
```

**「最近動いた」を条件に含めるのは、放置された案でスコアが開きっぱなしになるのを防ぐため。** 未確定であることだけを条件にすると、誰かが案を作って確定せずに放置しただけで**スコアが永久に見えたまま**になる。`finalized` を条件に入れた理由（1回目の分配以降ずっと見えたままにしない）が、確定されない案では達成できていなかった。

最終更新は「作成日時」と「編集ログの最新」の新しいほう。作成日時だけを見ると、数週間かけて議論している案が途中で非開示に落ちる。放置で閉じた場合も、案を編集すればまた開く。

判定に使う情報は既存の `DistributionProposal` にある（`finalized` と作成・編集の時刻）。新しいフェーズ状態は持たない。この判定を採るのは、**「議論してから数字を見る」順序を構造的に強制できる**ため。変化ログを読む → 議論する → 案を作る → 初めてスコアが見える、という順序になり、「スコアは配分の出発点であって分配額そのものではない」（本ドキュメント「分配シミュレーション」）と一致する。フェーズ状態は単なるスイッチで、この順序までは担保しない。

確定後に非開示へ戻しても情報は失われない。確定した案は `DistributionItem` に当時の数値を保持しており、隠れるのはライブの `/scores` だけで、むしろ「確定した案はスナップショット」という意味が明確になる。

| 経路 | 状態 |
|---|---|
| `GET /projects/{id}/scores` | 判定を満たさなければ 403（`SCORES_NOT_DISCLOSED`）。判定は `services/scoring.py` の `can_disclose_scores()` に1箇所だけ置く |
| 画面7（サイドバーの常設リンク） | リンクは常設のまま。**画面には入れるがスコアは出ず**、非開示の理由（案が無い／確定済み／30日更新なし）に応じた説明に置き換わる。リンクを隠すと分配を始める導線まで消えるため |

**分配案の作成は確認ダイアログを挟む。** このボタンは押した瞬間にチーム全員へスコアを開示する。下の「受け入れる制約」は *見えるかたちで意図的な行為をする必要がある* ことを抑止の根拠にしているが、**押した本人にその意味が見えていなければ抑止は成立しない**。ダイアログでは開示されること・作成者が記録されること・確定または30日で非開示に戻ることを伝える。ダイアログは案の名前と報酬総額も受け取るので常に開く。すでに開示中（他に検討中の案がある）なら開示状態は変わらないため、**開示の説明だけを出さない**。

**ゲートはクライアントへの開示にのみ掛け、サーバ内部の計算は制限しない。** `services/distribution.py` が案の作成・重み変更時に `scoring.get_project_scores()` を呼んで初期比率を作っており、そこまで塞ぐと鶏卵問題になる（案を作れないのでスコアが見えず、スコアが見えないので案が作れない）。素通しの `get_project_scores()` と、判定付きの `get_scores_for_disclosure()` を分けることで両立させている。

> **受け入れる制約**: 誰でも分配案を作れるため、**ダミーの案を作ればスコアは見られる**。技術的な壁にはならない。これは許容する。`created_by` が記録され編集履歴は全員に公開されるため、**見えるかたちで意図的な行為をする必要がある**からである。画面7の不正操作対策（「全員に編集履歴が公開されることで社会的抑止力を担保。承認制は過剰設計として不採用」）と同じ考え方で一貫させる。ここに明記しておくのは、後から抜け道として再発見されないようにするため。

> 設計の出典: [エンジニア成果測定論（Zenn）](https://zenn.dev/awesome_kou/articles/engineer-performance-metrics)

## 変化ログと貢献サマリー

> 「作業ログではなく、変化のログを残す」。件数ではなく「何をどう変えたか」を可視化し、スコアの定性的な根拠とする。

一覧（土台）→ 詳細（AI）の2層で構成する。**AIはクリティカルパス外**で、AIが落ちても第1層は機能する。

### 第1層: 変化ログ（AIなし・土台）

既存キャッシュ（`GitHubPullRequest` / `GitHubIssue` / `GitHubReview`）から、メンバーごとに「いつ・どのPR/Issue/レビューを・何を（タイトル）」を時系列に並べた一覧。新規データ収集もAIも不要。一次情報（`html_url`）リンクを必ず併記する。スコアと同じ生データだが、**数字に潰す前の姿を出すこと自体がGoodhart対策**（数字の降格）。ダッシュボード・メンバー詳細・分配画面の骨格となる。

### 第2層: 貢献サマリー（AI・変化ログの詳細）

> AIの唯一の用途。

変化ログの各エントリ（および期間・メンバー単位）の**詳細**を、Claude APIが一次情報（PR本文・diff・レビューコメント）から要約する。第1層の"目次"に対する"詳細"であり、主役/副次ではなく一覧→詳細のドリルダウン関係。スコアの根拠補完および就活・実績証明としての利用を想定。

- **エビデンスを閉じる**: 各主張は必ず根拠PR/diffへのリンクを伴う。無根拠の主張をさせない。ハルシネーションしても一次情報で検証・棄却できる。
- **報酬のクリティカルパス外**: 分配額を自動決定しない。最終文は人間が読み、必要なら書き足す。
- **生成方針**: 振り返り/分配時にオンデマンド・低頻度で生成（Haiku＋2層キャッシュ）。PR単位の定期・自動生成はしない。再生成は事後の手動オンデマンドに限る。

| フェーズ | データソース | 内容 |
|---|---|---|
| MVP | GitHubコミット・PR・diff | メンバー/PR単位の貢献サマリーを生成 |
| Post-MVP | GitHub + Discordログ | 議論・意思決定の文脈も含めたサマリーに強化 |
