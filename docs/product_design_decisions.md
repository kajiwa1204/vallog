# Vallog — 設計決定事項まとめ

> 最終更新: 2026-05-07

---

## 1. プロダクト概要

| 項目 | 内容 |
|---|---|
| プロダクト名 | Vallog |
| 対象ユーザー | GitHubを中心に動く3〜8人のハッカソン・副業チーム |
| 解決する課題 | 貢献の感覚が人によって異なり、賞金・報酬の分配合意が取れない |
| コアバリュー | 判断の根拠は透明に、評価の主体はチームに |

---

## 2. 設計思想

- **「AIが評価を決めない」設計**
  AIはDiscordや議事録の要約・コンテキスト整理に留める。スコアリングや分配の決定はチームが行う。

- **客観データを根拠にした合意形成**
  GitHubの客観データをベースに、分配の合意プロセスをサポートする。

---

## 3. スコアリング設計

### 3-1. カテゴリ構成

| カテゴリ | 種別 | デフォルト重み |
|---|---|---|
| GitHub活動量 | スコア対象 | 40% |
| タスク完了スピード | スコア対象 | 35% |
| 品質・可用性 | スコア対象 | 25% |
| 議論・コミュニケーション | コンテキスト（スコア外） | — |

> **重みのカスタマイズ**: チームごとに変更可能

---

### 3-2. 各カテゴリの指標

#### GitHub活動量（40%）

| 指標 | 詳細 |
|---|---|
| Issue / PR 立ち上げ数 | 設計・デザイン・リファクタへの関与も含む |
| コードレビュー貢献 | コメント1件以上のレビューのみカウント |
| Approve / Request changes 回数 | — |
| ターンアラウンドタイム | PR到着からレビューまでの時間 |

カテゴリ内の合成: **均等割り**（後から調整可）

---

#### タスク完了スピード（35%）

| 項目 | 詳細 |
|---|---|
| 計測式 | 獲得SP ÷ 経過時間 |
| SP入力方法 | **GitHub IssuesのラベルでSPを設定**（例: `SP:1` / `SP:2` / `SP:3` / `SP:5` / `SP:8`）|
| 計測区間 | アサインからPRマージまで |
| 前提 | **GitHub Projects運用**を必須とする |

---

#### 品質・可用性（25%）

| 指標 | 詳細 |
|---|---|
| 機能ごとの可用性スコア | 実装者以外のメンバーがレビュー・検証 |
| 手戻り率（バグ起因） | バグ報告数 + PR再オープン回数で計測 |

---

#### 議論・コミュニケーション（コンテキスト・スコア外）

| チャネル | 取得方法 | AIの役割 |
|---|---|---|
| Discord（オンライン） | Discord API でログ取得 | Claude APIで要約・議論レビューとして表示 |
| 議事録（オフライン） | 手動入力 or アップロード | 要約・保存のみ（Draft扱い） |

> スコアには一切影響しない。可視化・要約のみ。

---

## 4. 分配シミュレーション

- 各メンバーの分配比率 = 総合スコア ÷ チーム全体の総合スコア合計で算出（AIは使用しない）
- 算出された比率を「参考値」として提示し、チームが手動で調整できる
- 最終的な分配の決定はチームが行う

## 5. MVPスコープ

### 5-1. 対象機能

| # | 機能ブロック | 内容 |
|---|---|---|
| A | GitHubデータ取得・スコア算出 | Issue/PR/レビュー/TAT/SPラベル |
| B | スコアの可視化 | カテゴリ別・メンバー別ダッシュボード |
| C | 分配シミュレーション | 重みカスタマイズ＋複数案の比較 |
| D | コミュニケーション定量化 | Discordの発言数・リアクション数 |

### 5-2. MVP対象外（Post-MVP）

| フェーズ | 機能 |
|---|---|
| Post-MVP ① | AI要約（Claude APIによるDiscordログの要約）← AIの唯一の用途 |
| Post-MVP ② | 実際のログ表示 |
| Post-MVP ③ | Slack連携 |
| Post-MVP ④ | 期間フィルター |
| Post-MVP ⑤ | リアルタイム更新（WebSocket） |

### 5-3. データ更新方式

- **オンデマンド取得**（リロード時に最新データを取得して再描画）
- リアルタイム更新（WebSocket）はMVP対象外

## 6. 画面設計

### 6-1. 画面一覧

| # | 画面名 | 役割 |
|---|---|---|
| 1 | ログイン | GitHub OAuth認証 |
| 2 | プロジェクト一覧 | 参加中プロジェクトの一覧・新規登録 |
| 3 | プロジェクト設定 | リポジトリ確認・メンバー確認・重み設定・招待リンク発行 |
| 4 | ダッシュボード | メンバー別スコア一覧＋コミュニケーション定量サマリー |
| 5 | メンバー詳細 | カテゴリ別スコア内訳 |
| 6 | コミュニケーション詳細 | Discordの定量データ（ダッシュボードからの遷移） |
| 7 | 分配シミュレーション | 重み調整・複数案の比較・合意 |

### 6-2. 画面遷移の設計方針

- ダッシュボード（4）にコミュニケーション定量サマリーを表示し、詳細はコミュニケーション詳細画面（6）に遷移
- メンバー詳細（5）もダッシュボード（4）からの遷移

### 6-3. プロジェクト参加方式

- **招待リンク方式**を採用
- フロー: プロジェクト作成 → 招待リンク発行 → メンバーがリンクを踏む → GitHub OAuthでログイン → 参加完了
- GitHub Organization連携は不採用（ハッカソンチームへの課金負担を避けるため）

### 6-4. プロジェクト管理

- 1ユーザーが複数プロジェクトに参加可能（Slackのワークスペースモデル）

### 画面7: 分配シミュレーション

| 項目 | 内容 |
|---|---|
| 叩き台の提示 | スコア比率をもとに分配の参考値を表示（「参考値」と明示） |
| 手動調整 | メンバー全員が数値を自由に編集できる |
| 編集履歴 | 誰がいつ何を変更したかをタイムライン表示・全員に公開 |
| 重みの調整 | この画面上でその場で調整・複数案を比較 |

| 設計思想との整合 | システムは提案のみ・決定はチームが行う |

> **不正操作への対策**: 全員に編集履歴が公開されることで社会的抑止力を担保。承認制は過剰設計として不採用。

## 8. 技術スタック

### 8-1. 確定スタック

| レイヤー | 技術 | 選定理由 |
|---|---|---|
| フロントエンド | Next.js | Cloudflare Tunnel前提で同一オリジン構成が活きる・SSRをダッシュボード初期取得に活用できる |
| バックエンド | FastAPI | Venduce実績あり |
| DB | PostgreSQL | Venduce実績あり |
| 認証 | GitHub OAuthのみ | ログイン手段はGitHub一本 |
| トークン管理 | アクセストークン（メモリ保持）+ リフレッシュトークン（HttpOnly Cookie） | XSS耐性とモバイル拡張性を両立するベストプラクティス |
| インフラ | Docker Compose + Cloudflare Tunnel | 環境再現性・チーム参入コストの低さ・Venduceからの流用 |
| リバースプロキシ | nginx | 同一オリジン化・APIプレフィックス統一 |
| ホスティング | Proxmox上のUbuntu Server（VM1台） | Docker直よりオーバーヘッド小・チームのインフラ構成に合わせる |

### 8-2. APIルーティング設計

- バックエンドのエンドポイントは **`/api/*` に統一**
- フロント・バック間のパス衝突を構造的に防ぐ
[ブラウザ]
└── https://vallog.com
└── Cloudflare Tunnel
└── nginx:80
├── /api/*  → FastAPI (uvicorn)
└── /*      → Next.js (next start)

### 8-3. 開発環境の設計方針

開発環境ではNext.js Rewritesを使って同一オリジンを再現する。

```typescript
// next.config.ts
rewrites() {
  return [{ source: '/api/:path*', destination: 'http://localhost:8000/:path*' }]
}
```

- `NEXT_PUBLIC_API_BASE_URL` は空にしてRewritesに委譲
- 開発・本番ともにブラウザからは `/api/*` への単一オリジンリクエストになる

### 8-4. インフラ構成（VM1台構成
Proxmox
└── VM: Ubuntu Server
└── docker compose up
├── nginx
├── Next.js (next start)
├── FastAPI (uvicorn)
├── PostgreSQL
└── cloudflared（本番のみ・profiles: production）

VM1台にまとめる理由: SSH接続先が増えることによる運用コストを避けるため。DBのスナップショットはVM全体のProxmoxスナップショットで代替する。
