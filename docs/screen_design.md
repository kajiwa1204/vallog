# Vallog — 画面設計

## 画面一覧

| # | 画面名 | 役割 | MVP |
|---|---|---|---|
| 1 | ログイン | GitHub OAuth認証 | ✅ |
| 2 | プロジェクト一覧 | 参加中プロジェクトの一覧・新規登録 | ✅ |
| 3 | プロジェクト設定 | リポジトリ確認・メンバー確認・重み設定・招待リンク発行 | ✅ |
| 4 | ダッシュボード | チームの変化ログ（貢献アクティビティ）＋チーム状況パネル（スコアは非表示） | ✅ |
| 5 | メンバー詳細 | 変化ログ・貢献サマリー・各指標の生データ（スコアは非表示） | ✅ |
| 6 | コミュニケーション詳細 | Discordの定量データ | Post-MVP |
| 7 | 分配シミュレーション | 重み調整・複数案の比較・合意 | ✅ |

## 画面遷移の設計方針

- メンバー詳細（5）はダッシュボード（4）からの遷移
- コミュニケーション詳細（6）はPost-MVP対象のためMVPでは非表示

## プロジェクト参加方式

- **招待リンク方式**を採用
- フロー: プロジェクト作成 → 招待リンク発行 → メンバーがリンクを踏む → GitHub OAuthでログイン → **GitHubリポジトリのアクセス権確認** → 参加完了
- 招待リンクは7日間有効・使用回数無制限（チームで使いまわせる）
- privateリポジトリの場合、アクセス権のないGitHubアカウントは参加を拒否する
- GitHub Organization連携は不採用（有志開発チームへの課金負担を避けるため）

## 認可設計

全メンバー同等権限。ダッシュボード閲覧・分配シミュレーション編集・招待リンク発行・プロジェクト設定変更を全メンバーが実施できる。ロールベースのアクセス制御は不採用（フラットな有志開発チームが対象のため）。

## プロジェクト管理

- 1ユーザーが複数プロジェクトに参加可能（Slackのワークスペースモデル）

### 画面4: ダッシュボード

**位置づけ: 日常の入口。** メンバーが日常的に開き、「自分は今日、何かする必要があるか」に最初に答える画面とする（振り返り・分配専用の面にはしない）。したがって最優先は `気にかけること` の視認性で、自分に用事が無いこともひと目で分かる必要がある。振り返り・分配は画面7が担う。

主役はチームの**変化ログ**（誰がいつどのPR/Issueを何を、の時系列一覧＋一次リンク）。**この画面にスコアは出さない**（数字を主役にしない・Goodhart対策の③事前既知を折る。開示は画面7。`docs/scoring_design.md`「Goodhart対策とスコアの事後開示」参照）。日常的に開く画面でスコアが見えないことは、③事前既知を折る設計と整合する。スコアの代わりに、チームがいま何を動かしているかを映す運用パネルを置く。

| 項目 | 内容 |
|---|---|
| チーム変化ログ | メンバー別の直近アクティビティ（PR/Issueの時系列一覧＋GitHub一次リンク）。AIなしで表示（第1層・土台）。日付ごとに束ね、前回訪問以降の変化に印を付ける |
| 活動リズム（pulse） | 直近N日の日次バケット。PR/Issue/レビューのtimestampを集計。直前の同じ長さの期間との差を添える（単独の件数には多い/少ないの基準がないため） |
| 気にかけること（attention） | レビュー待ちPR（24h経過後）・**修正待ちPR**（最終レビューが CHANGES_REQUESTED）・停滞Issue（assigned後7日）・draft |
| 最近片づいたもの | マージされたPR・完了したIssueを新しい順に数件。attention の裏返し |
| 動いている領域（themes） | Issueのラベル集計（全期間）。ラベル名の名前空間（`epic:` / `priority:` など）で束ねる |
| 自分の目印 | attention を「あなたがレビューできます / あなたの番です / あなたのPRが待っています / チームの状況」に畳み、変化ログの絞り込みチップでは自分を先頭に固定する（順位は出さない） |
| スコア | **表示しない**（画面7で事後開示） |
| 期間フィルター | なし（全期間表示・Post-MVPで追加） |
| 遷移先 | メンバー詳細（画面5） |

運用パネル4種は `GET /projects/{id}/dashboard` が1レスポンスで返す。同一のデータ源を4通りに畳むだけなので、新規テーブルもAIも不要で、既存のGitHubキャッシュの読み取りだけで足りる。「前回いつ見たか」だけはクライアントの状態なので `localStorage` に置き、サーバには持たせない。

> **attention を「誰の番か」で畳む理由**: 全員分をフラットに並べると、件数は出ても「自分が次に何をすればいいか」に変換されない。**動かせるのが誰か**で群を分けると、同じデータが行動になる。自分のPRのレビュー待ちを「あなたの番」に入れないのは、動かせるのがレビュアーであって作者ではないため（混ぜると他人の未着手を自分の停滞として突きつけることになる）。なお「あなたがレビューできます」は GitHub の `requested_reviewers` ではなく他者レビューが1件も無いPRなので、**依頼されたのではなく手を挙げられる**という意味に留める。

> **「最近片づいたもの」を置く理由**: attention は止まっているものしか出さないため、放っておくとこの画面は負の情報だけを毎日見せる面になる。無給の有志チームでは進んだ実感が続ける理由になる。ただし**人ごとの件数には畳まない**（畳んだ瞬間に「誰が多いか」の序列になり、下記の理由でこの画面が出さないと決めた集約に戻る）。

> **パネルがスコアにならない理由**: 4種はいずれも重み付けをせず、報酬の算定式には現れない。「レビュー待ちが3件ある」は誰かの評価ではなく、チームが次に手を付ける先を指すだけ。
>
> ただし attention の停滞時間は、Issueがクローズされた時点でスピードカテゴリの経過時間に連続する（どちらも起点が `assigned_at`）。それを承知で残すのは、止まっているものを動かすには持ち主と経過が要るためで、行動可能性を優先した判断である。
>
> 一方、レビュー本数のように**安く積める量**を個人別に集約して序列化するパネルは置かない。変化ログが1件ずつに脱集約している情報を画面が再集約し直すことになり、「数字の降格」（`docs/scoring_design.md`）に反するため。当初あった「レビューの流れ（reviewer → PR author の件数）」はこの理由で取り下げた。

### 画面5: メンバー詳細

そのメンバーの**変化ログ**（PR/Issueの時系列＋一次リンク）を主軸に、その詳細としてサマリーと生データを提示する。**この画面にもスコアは出さない**（画面4と同じ理由。ダッシュボードから1クリックで飛べるため、ここに残すと③事前既知が折れない）。

| 項目 | 内容 |
|---|---|
| 変化ログ | そのメンバーのPR/Issueの時系列一覧＋GitHub直リンク（第1層・土台・AIなし。根拠の透明化） |
| 貢献サマリー | 変化ログの各エントリ/期間の詳細をClaude APIで要約（第2層・根拠リンク併記）（Feature D） |
| 各指標の生データ | PR件数・レビュー数などの具体的な数値（重み付けも順位付けもしない事実なのでスコアには当たらない） |
| カテゴリ別スコア内訳 | **表示しない**（画面7で事後開示） |
| 時系列グラフ | 活動量の推移（週次） |
| 他メンバーとの比較 | なし（Post-MVP） |

#13 で変化ログの絞り込みが自分を先頭に固定した結果、この画面は「他人の成績を見に行く画面」ではなく**自分の貢献が正しく記録されているかを検算する画面**の性格を強く持つ。無給の有志チームでは「自分の働きが見られているか分からない」ことが離脱要因になり、スコアを外した以上、その不安を埋めるのは順位ではなく記録の確認可能性になるため。

> **生データをサーバで集計せず、表示中の変化ログから数える理由**: 検算が用途なので、**画面に出ている数字は下の一覧を数えれば必ず再現できる**必要がある。サーバがキャッシュ全件から別途集計すると、表示行を数えても合わない数字が出て用途そのものが壊れる。代償は `limit` による打ち切りで、これは「直近◯件から数えた」と母数を画面に明示して引き受ける。

> **グラフを日次ではなく週次にする理由**: 個人の活動はチームより疎で、画面4と同じ日次バケットだと大半が空バーになりリズムが読めない。打ち切りに掛かっている場合、いちばん古い週はその週の一部しか手元に無いので描かない（低いバーとして出ると事実に反する）。

> **人を切り替える導線を置く理由**: 検算が主用途でも、他メンバーの記録に行けなくする理由はない。無給の有志チームでは「誰が何をしているか」を互いに知れることが協調の前提になる。導線はダッシュボードの絞り込みバー（「メンバー詳細 →」）と、この画面上部のメンバー切り替えチップの2つ。並びはダッシュボードの絞り込みチップと同じく自分を先頭に固定し、残りは辞書順にする（活動量順に並べると、この画面が出さないと決めた序列がそこに現れる）。

### 画面7: 分配シミュレーション

| 項目 | 内容 |
|---|---|
| 変化ログの表示 | 主役は各メンバーの変化ログ（第1層・PR/Issue時系列＋一次リンク）を画面上部に表示 |
| 貢献サマリーの表示 | 変化ログの詳細として貢献サマリー（Feature D）を展開（第2層・根拠リンク併記） |
| スコアの参照 | GitHubスコアを画面下部に小さく表示（補助情報として配置） |
| 手動調整 | メンバー全員が数値を自由に編集できる。調整時に理由の入力を必須とする |
| 編集履歴 | 誰がいつ何を変更したか・その理由をタイムライン表示・全員に公開 |
| 重みの調整 | この画面上でその場で調整・複数案を比較 |
| 報酬総額の入力 | 任意入力（未入力時は貢献度の割合のみ表示） |
| 合意の記録 | チームで確定した分配案をVallog上に永続化 |

> **不正操作への対策**: 全員に編集履歴が公開されることで社会的抑止力を担保。承認制は過剰設計として不採用。
