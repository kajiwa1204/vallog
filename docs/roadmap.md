# ロードマップ

Vallog の開発ロードマップ。GitHub Projects（`@kajiwa1204's vallog project`）と連動し、各フェーズを Milestone で管理する。

> **前提**: `feat/prototype` ブランチは設計検証のためのプロトタイプ（使い捨て）。本実装は本ロードマップに沿って別スケジュールで進める。プロトタイプで得た知見は Phase 2 以降の Issue として記録済み。

> **最終締め切り: 2026-08-31。コア機能（Phase 1）は 2026-07-25 までに完成させる**（当初は7月中旬目標だったが、サマリー基盤一式をMVPに取り込んだため再設定）。

---

## フェーズ概要

| フェーズ | ゴール | 期日 | Milestone |
|---|---|---|---|
| Phase 1 | MVP実装（コア機能 + サマリー基盤 + テスト基盤） | **2026-07-25** | `Phase 1: MVP実装` |
| Phase 2 | ハードニング（テストカバレッジ拡充 + プロトタイプ知見の反映） | 2026-08-10 | `Phase 2: ハードニング` |
| Phase 3 | 本番化（デプロイ・運用・コスト監視） | **2026-08-31** | `Phase 3: 本番化` |
| Phase 4 | 将来構想（HRテック横展開） | 締め切り後 | `Phase 4: 将来構想` |

### スケジュールの考え方
- **〜7/25（Phase 1）**: コア機能 + サマリー基盤を一通り動く状態にする。最優先。**テスト基盤（pytest + CI）はスコア計算より先に整え、スコア・分配ロジックはテストとセットで実装する**（品質保証を人間レビューだけに依存させない）。
- **〜8/10（Phase 2）**: テストカバレッジを広げて品質を固める。
- **〜8/31（Phase 3）**: 本番デプロイ・運用整備。**8/31が最終締め切り**。
- Phase 4 は締め切り後の検討事項（実装スコープ外）。

当初設計（`docs/screen_design.md` / `docs/scoring_design.md`）に基づくコア機能の本実装。プロトタイプで実現性は検証済み。貢献サマリー機能は「コスト制約」の観点から、プロトタイプ知見をMVPに取り込む。

- 基盤セットアップ（FastAPI / Next.js / Alembic） — #3, #4, #5
- GitHub OAuth認証（バックエンド / フロントエンド） — #6, #7
- プロジェクトCRUD + 招待リンク + UI — #8, #9
- **テスト基盤（pytest + CI）+ スコア・分配ロジックのテスト — #66**（#36 から分割・前倒し。CI基盤は #12 着手前に完了させる。スコア・分配はプロトタイプの入出力から特性テストを起こし、期待値を固定してから実装する）
- GitHubデータ取得・TTLキャッシュ・スコア計算 — #10, #11, #12
- ダッシュボード / メンバー詳細画面 — #13, #14
- 貢献サマリー基盤（プロトタイプ知見を反映した本実装） — #30, #34, #31, #32, #33, #16
  - #30 LLMプロバイダ抽象化（Claude / OpenAI互換 / Ollama）
  - #34 diffベースPR要約（lockファイル除外・head_shaキャッシュ判定）
  - #31 2層キャッシュ（PR単位 Tier1 / メンバー Tier2）
  - #32 バックグラウンドジョブ基盤（生成は数分かかるため非同期必須）
  - #33 PR単位の個別サマリー生成・強制再生成

- 分配シミュレーション（CRUD・編集ログ・画面） — #17, #18

> 当初 #15「Claude APIクライアント + 生成 + キャッシュ」は #30/#34/#31/#32/#33 に分割・再設計したため superseded でクローズ。
> 当初 #35「OAuthセットアップウィザード」は env 方式への統一決定（#58）により撤回・クローズ。

### クリティカルパスと所要見込み
依存を尊重すると、サマリー基盤チェーン `#30 → #34 → #31 → #32 → #33 → #16` と分配チェーン `#66(CI・テスト基盤) → #12 → #17 → #18` が律速。2バックエンド + 1〜2フロントエンドの並走を前提に、コア完成は **実勢 7/25 頃**（末端は #16 サマリー表示）。#66 のCI基盤部分は小さく（1〜2日想定）、特性テストは #12/#17 の実装と並走できるため、前倒しによる期日への影響は限定的。それでも遅れる場合は #32/#33/#16（一括生成・個別生成・表示の一部）を後ろ倒しするなどスコープ調整で吸収し、**テストを削って取り戻すことはしない**。

## 運用ルール

- 各 Issue は Milestone（フェーズ）と epic ラベルで分類する。
- 進捗は GitHub Projects の Status（Todo / In Progress / Done）で管理する。
- プロトタイプで得た知見は、対応する本実装 Issue の本文に「プロトタイプで判明した罠」として記録する。
